# Decisions Log — LossGuard

Documents *why* we made key choices, not just what we built. Cross-referenced
from research-notes.md and dataset-schema.md.

---

## D1 — LLM used only for explanation, never for decisions

**Decision:** The explanation layer (`app/explain/explain_service.py`)
receives a structured evidence JSON and returns a human-readable summary.
It never scores risk, never sets the decision tier, and is architecturally
isolated (read-only module, no DB write access, no ability to trigger
`/decision`).

**Current implementation status:** in this submission, `explain_service.py`
is a deterministic template — it formats the evidence fields into a
sentence, it does not call a real LLM API. This was a conscious
time-tradeoff, not a hidden shortcut: the function signature and evidence
schema are already shaped so that swapping the template body for a real
Gemini/Groq call is a same-file change. We call this out explicitly rather
than implying a live API call, since the distinction matters for how the
project should be evaluated.

**Why isolate it this way regardless of template-vs-live:** Money
decisions need to be deterministic and auditable. LLMs are probabilistic
and not reliably reproducible — using one to gate a real financial/account
action would violate the track's "strictly defense-only" requirement in
spirit, even if not in a literal offensive-capability sense. See
research-notes.md §7.

## D2 — No Temporal Graph Neural Network; snapshot-based NetworkX instead

**Decision:** Early/evolving ring-formation detection uses periodic
snapshot graphs (NetworkX connected components at different time cuts),
not a trained TGNN.

**Why:** TGNNs are the state-of-the-art academic approach (research-notes.md
§3) but require GPU training infrastructure and tuning time we don't have
solo in a 15-day build. The snapshot approach captures the same core
insight — clusters becoming visible over time — at a fraction of the
implementation risk.

---

## D3 — Simulated device_id, not real fingerprinting

**Decision:** `device_id` is a synthetic field, not generated by a real
fingerprinting library (e.g. FingerprintJS).

**Why:** Real device fingerprinting requires a dedicated third-party
service integrated at checkout — out of scope for a synthetic-data
hackathon build. Documented explicitly rather than presented as if real.

## D4 — Dataset iteration: fixing accidental "giveaway" features

Three rounds of synthetic-data bugs were found and fixed via diagnostic
scripts (`app/ml/diagnose_leakage.py`) rather than by chasing metrics blindly:

1. **`category_return_concentration` leakage** — fraud rings were
   force-assigned a single order category, making concentration always
   exactly 1.0 (separation ratio 5.63 vs 0.1-0.7 for every other feature).
   Fixed by mixing 1-3 orders from other categories into ring members.
2. **`cluster_size` as a tautological proxy** — genuine users had zero
   organic device/address sharing, so "cluster_size > 1" was a perfect
   fraud/genuine separator by construction, not a learned insight. Fixed by
   adding ~15% organic sharing among genuine users (family/roommate
   pattern), so cluster sizes overlap between genuine and fraud-ring users.
3. **Fraud-ring behavioral rate too extreme** — initial return-rate range
   (30-45%) sat clearly above genuine apparel buyers (25-40%), making
   behavior alone too separable. Tuned to 20-35% to force real overlap.

**Why this matters for evaluation:** each fix was diagnosed with a
per-feature separation-ratio check before changing anything, and each
round's result is logged in `docs/journal/`. This is deliberate — the
track evaluates debugging/iteration quality, not a story where "everything
worked the first time."

## D5 — Honest metrics: what we didn't over-tune

**Current state (locked for Phase 5+):** behavioral-only baseline: recall
0.765, precision 0.722. Behavioral+structural combined: recall 0.853,
precision 1.000. Net cost of errors dropped ~26% (₹56,291 → ₹41,691) by
adding the graph layer.

**Known limitation, stated rather than hidden:** precision of 1.000 on the
combined model is partly a function of a moderate test-set size (34 fraud
cases held out). `cluster_size` remains the single largest feature
contributor (56%) in the combined model, though 5+ other features now
meaningfully contribute (a marked improvement from an earlier iteration
where cluster_size alone drove ~78-93% of importance).

**We deliberately stopped tuning here** rather than chasing a "less
perfect-looking" precision number, because further changes past this point
offered diminishing returns relative to time spent, and the current result
is already defensible and honestly documented.

## D6 — Future improvements (explicitly scoped OUT of the current build)

Listed here so they read as conscious scope decisions, not oversights:

1. **Larger dataset** — current genuine-user count (800) yields a modest
   held-out fraud count (~34 cases). Scaling to 2,000+ genuine users would
   give a statistically sturdier test set and likely soften the
   precision=1.000 result to something less coincidental-looking.
2. **Cross-validation** — currently a single stratified train/test split.
   K-fold CV would report metric variance, not just a point estimate.
3. **Heterogeneous fraud archetypes** — all synthetic fraud rings currently
   follow one generation pattern (moderate behavior + partial structural
   sharing). Adding 2-3 distinct archetypes (e.g. a "behavior-quiet,
   structure-heavy" ring vs a "structure-quiet, behavior-erratic" ring)
   would stress-test the model's robustness more realistically.

These are natural next steps if time remains after the core pipeline
(decision engine, backend API, frontend, LLM explanation layer) is done —
not required for a working submission.
